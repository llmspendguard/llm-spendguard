# Capability architecture

Spendguard governs and records model use across metered APIs and subscription CLI lanes, routes work, measures quality and economics, and reconciles captured activity against available provider evidence. **Read this map before designing a feature.** Each entry below is source-read and built-and-verified unless marked **PARTIAL**, **STUB**, or **VISION**; verification here means implementation inspection, not a live-provider integration test. PARTIAL names a missing guarantee or wiring limit, not an absent module. Paths are relative to this repository; entry-point citations are navigable source locations. Billed API dollars, flat subscription fees, and remote compute are real costs; subscription usage's estimated value is a separate axis and must never be added to them.

## Routing and contracts

### Provider registration contract

`adapters.register_provider(name, base_url, key_env, prefixes, kind="openai")` adds an endpoint/key/prefix specification; `kind` selects the OpenAI-compatible or Anthropic SDK path. For example, an application can call `adapters.register_provider(provider_name, base_url=endpoint, key_env=credential_env, prefixes=model_prefixes)` using its configuration. `provider_for` accepts explicit `provider:model` IDs; otherwise the longest matching registered prefix wins, and unknown providers raise (`src/spendguard/generate/execution/providers.py:32`, `src/spendguard/generate/execution/providers.py:32`). Registration supplies routing metadata, not a new enforcement implementation: the selected SDK surface still needs the installed gate described below.

## Prospective coalescing, durable queues and admission

Adapter queue registration also tracks foreground calls; it does not mean every adapter call executes through the queue drainer.

**These are different existing mechanisms, not names for one queue.** `storm_coalescer` is the prospective accumulation queue: it waits for arrivals before choosing realtime versus batch. `lane_queue` persists work and leases ownership across attempts and processes. `dispatch` and `xp_rate_window` admit calls against concurrency and RPM/TPM capacity. `whole_job` plans an already-known set of jobs across a horizon. `queue_planner` forecasts an existing backlog; it does not collect future arrivals.

## Batch submission, collection and bulk safety

`submit` and `callio` are provider Batch API legs, not prospective queues. They are called by storm executors, OpenAI whole-job execution, the durable tracker/offload path, bulk delegation's batch-on-miss path, and experiment/history workflows. Anthropic support exists in submit/collect but is not wired uniformly into every higher-level caller.

### Explicit submission contract

`guarded_submit` estimates first, refuses a count above `request_cap` (default 25,000), enforces `cap_dollars`, and refuses a projection above `expected_cost * overrun_tolerance`; the default tolerance is 1.2 (20% over expected; `src/spendguard/generate/execution/submit.py:112`). Its estimate-only path (`submit=False`) checks and writes an audit without submitting; normal submission also applies resilience checks and a live first-request preflight, which can itself bill. Accepted-batch booking is deferred until provider acceptance (`src/spendguard/generate/execution/submit.py:355`). Use separate estimate and approval stages before execution.

Pass a **measured per-request** `avg_out_tokens` to override output projection; a ceiling is a worst-case send limit, not evidence of typical output. The estimate reports both output and token-count bases, so inspect them before approving. Without tiktoken, the local counter warns about its `len(text)/4` approximation and recommends installing tiktoken in the gated venv before trusting a batch estimate (`src/spendguard/generate/execution/submit.py:79`). Provider-aware counting also exposes proxy/normalization bases: calibrate provider factors where appropriate rather than treating a character estimate as exact (`src/spendguard/generate/execution/submit.py:95`, `src/spendguard/analyze/cost_estimation/provider_tokens.py:183`, `src/spendguard/analyze/cost_estimation/content_tokens.py:317`). This does not imply that every estimator uses `max_tokens` or that every estimate is conservative.

## Config, installation and gate

`config.py` is the runtime resolver; `config_schema.py` describes settings for surfaces/onboarding. `_cfg_get` reads literal section/key pairs. **Environment override support is individually implemented, not a universal dotted-key convention.** In particular advisor numeric accessors are config-only and preserve zero; schema metadata alone does not prove an environment override is wired. Pool settings and selected other controls have explicit environment handling.

### Enforcement order and cap scopes

For a batch estimate, `_decide_and_account` first routes a `spendguard:*` intent to the meta cage and returns. Ordinary work then passes batch-1 discipline and bulk-evidence checks, cross-process daily/monthly checks, the per-batch cap on the realistic projection, and a **separate worst-case ceiling check**, before recording. Submitters can defer recording until provider acceptance; otherwise the final step books a provisional estimate and an optional call-corpus row (`src/spendguard/manage/admission/gate.py:787`, `src/spendguard/manage/admission/gate.py:787`). Estimation is not a guarantee of known final batch cost.

### Kill switch and recovery

`GATE_DISABLE=1` or the persistent `$SPENDGUARD_HOME/disabled` flag disables enforcement; the default flag location is `~/.spendguard/disabled` (`src/spendguard/store/configuration/config_store.py:26`, `src/spendguard/store/configuration/config_store.py:897`). `spendguard off` writes the flag; `spendguard on` removes it. Clear the environment override too when recovering (`src/spendguard/manage/admission/gate.py:2580`). The generated startup hook checks both switches **before importing spendguard**, providing an escape hatch even if package import is broken; both the site/user hook and `.pth` bootstrap contain that check (`src/spendguard/platform/setup.py:217`, `src/spendguard/platform/setup.py:234`). Re-enabling the switches still requires installation in the interpreter actually used; the inventory's `require()` and SDK-coverage caveats apply.

### Registering an SDK gate

`spendguard.register(module_path, class_name, method, gate_fn, is_async=False)` appends a surface; the next `spendguard.install()` patches it alongside built-ins. For example, `spendguard.register(sdk_module, sdk_class, sdk_method, check_request)` followed by `spendguard.install()` uses application-supplied configuration and a callback. `gate_fn(kw, args)` returns to allow or raises `SpendGateRefused` (including its subclasses) to stop; an estimator can explicitly reuse `_decide_and_account` with the pipeline's estimate shape (`provider`, `model`, `requests`, `in_tok`, `out_tok`, `cost`, and any additional estimate basis fields). Registration itself does not invent estimation or post-call actual-usage accounting (`src/spendguard/interface/crossllm.py:242`, `src/spendguard/interface/crossllm.py:242`).

`_guard` propagates deliberate refusal but warns and permits on other callback errors. `install` is idempotent at patched methods and contains per-surface installation failures; its optional `cap` argument sets `GATE_CAP` for this process (`src/spendguard/manage/admission/gate.py:2312`, `src/spendguard/manage/admission/gate.py:2342`). Extension authors inherit this fail-open boundary and must not mistake successful registration for comprehensive fail-closed SDK coverage.

## Canonical money ledger and capture

### Storage, identity and isolation

`SPENDGUARD_HOME` selects state storage, defaulting to `~/.spendguard`; operational `config.json` and credential `keys.env` are separate files (`src/spendguard/store/configuration/provider_keys.py:-18`, `src/spendguard/store/configuration/provider_keys.py:-7`). Email/server credentials use dedicated `email.json`/`saas.json`, gitignored configuration files or environment variables rather than tracked project config (`src/spendguard/store/configuration/ledger_connection.py:821`, `src/spendguard/store/configuration/ledger_connection.py:865`). The canonical money ledger coexists with call, I/O and learning tables; the queue has its own database, as described below. This is not a claim that every subsystem shares one database.

Charge project resolution is `SPENDGUARD_PROJECT` → repository `.spendguard.json` SaaS project → git-root basename → cwd basename. Conversation identity checks `SPENDGUARD_CONV` → `SPENDGUARD_CHAT` → `CLAUDE_SESSION_ID` → process fallback (`src/spendguard/manage/admission/budget.py:74`, `src/spendguard/manage/admission/budget.py:106`). Contributor resolution uses explicit configuration, then git email, then a persisted anonymous machine identity (`usr_<hex>`); anonymous identity is attribution fallback, not proof of a resolved human/org owner (`src/spendguard/egress/saas.py:201`, `src/spendguard/store/configuration/ledger_connection.py:892`).

Ledger connections use WAL and thread-local pooling. Cross-connection work must commit in phases to avoid holding one writer while another connection attempts to write the same file; history reconstruction documents this ordering explicitly (`src/spendguard/store/configuration/ledger_connection.py:642`, `src/spendguard/store/configuration/ledger_connection.py:694`, `src/spendguard/analyze/learning/history.py:149`). These phases are not an atomic multi-module transaction. Daily/monthly caps remain **check-then-record**: concurrent processes can each pass before another records, allowing overshoot. High-volume realtime usage also incurs per-call ledger writes and shared SQLite writer contention; pooling reduces connection overhead but does not remove these limits (`src/spendguard/manage/admission/gate.py:612`, `src/spendguard/manage/admission/gate.py:787`, `src/spendguard/manage/admission/gate.py:1477`).

## Prices, catalogs and model parameters

### Price resolution and cache semantics

Lowest to highest precedence is built-in `_FALLBACK` → `$SPENDGUARD_HOME/litellm_prices.json` → `model_catalog.as_price_table()` rates → shipped `src/spendguard/prices.json` → `$SPENDGUARD_HOME/prices.json` → `$SPENDGUARD_HOME/prices.yaml` → the file selected by `SPENDGUARD_PRICES`. The home defaults to `~/.spendguard`; later layers merge per-model fields over earlier values (`src/spendguard/store/reference_data/pricing.py:22`, `src/spendguard/store/reference_data/pricing.py:41`, `src/spendguard/store/reference_data/pricing.py:78`). Supply provider/model rates in these data layers instead of embedding prices in application code; catalog capabilities and price provenance remain separate concerns.

`_cost` clamps cached input into `[0, in_tok]`. Realtime prices uncached input and cache reads separately, falling back to the full input rate when a cache-read price is absent. Batch uses explicit batch input/output rates and `batch_cached_in` when provided; without that cache-specific batch rate, cached input receives the ordinary batch-input rate. There is **no universal stacking of cache and 50% batch discounts** (`src/spendguard/store/reference_data/pricing.py:532`). Anthropic usage must be normalized because its ordinary `input_tokens` excludes cache-read/cache-creation tokens, while OpenAI's input count includes cached tokens; the gate adds cache reads before costing and passes cache creation separately (`src/spendguard/manage/admission/gate.py:1369`).

`cross_check_openrouter(run=False)` fetches public prices and performs exact-ID comparisons for free, returning unresolved identity and judgment work explicitly. Its default is a zero-spend, read-only drift check, not a semantic all-model price certification. `run=True` enables agentic identity and price-gap judgments and may spend; it does not silently rewrite the table (`src/spendguard/store/reference_data/pricing.py:429`).

## Learning and optimization

### Connected feedback loop

Opt-in physical-call capture and provider/history I/O recovery feed the call corpus; history mining, reconstruction and practice review create conditional insights. `brief`/`advise` and model recommendations consume that evidence; `experiment` tests cost and equivalence, and `promote` executes the selected path while retaining outputs for subsequent learning. Validation revisits insights as evidence changes; the gate enforces execution, reconciliation identifies capture gaps, and reporting surfaces results (`src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`, `src/spendguard/analyze/measurement/experiment.py:374`). This is a connected workflow, with the evidence-clipping, heuristic validation and partial-execution limits in the inventory below; a recommendation alone is not experimental proof. See [learning-advisor.md](learning-advisor.md), [MONEY-FLOW.md](MONEY-FLOW.md), [DATA_PLANE.md](DATA_PLANE.md), and [ROADMAP.md](ROADMAP.md).

### The governor governs its own spend

Internal calls labelled through `calls.context(intent="spendguard:…")` are recognized by the `spendguard:` prefix. Batch `_meta_gate` and realtime precheck/accounting route them to the separate daily meta cap and `kind='meta'` accounting, rather than workload caps. `budget.record_meta` tags project `llm-spendguard` in the canonical ledger: “separate meta ledger” means a separate accounting axis, not a separate database (`src/spendguard/manage/admission/budget.py:646`, `src/spendguard/manage/admission/budget.py:646`, `src/spendguard/manage/admission/budget.py:646`, `src/spendguard/manage/admission/budget.py:646`). `GATE_ALLOW` is an explicit meta-cap override too. This contract depends on labelling; it does not prove every internal call site is labelled.

Advisor corpus reads exclude `spendguard:%` intents so the governor's own analysis does not train its workload recommendations (`src/spendguard/store/spend_search/ledger_read.py:1022`). Advisor and judge models are configurable and must have pricing for reliable meta estimates. `validate_advisor` checks the configured `advisor.model` and `advisor.judge_model` against pricing and **returns problems**; that validator is not by itself proof every entry point refuses an unpriced model (`src/spendguard/store/configuration/ledger_connection.py:302`).

### Standalone client and server contract

Local gating, pricing, ledger, routing and local analysis require no team server; provider execution and fresh remote evidence still require their own connectivity. The opt-in SaaS seam uses a versioned `/v1` HTTP contract and a Bearer key; the server maps identity to its hierarchy rather than requiring callers to attach a trusted team/org identity to every request (`src/spendguard/egress/saas.py:136`, `src/spendguard/egress/saas.py:284`). `visibility=private` is the default. Normal upload paths return without pushing in that mode; enabled roll-ups select aggregate fields rather than prompts, outputs or keys. Connection does not authorize unresolved org ownership, and additional trust/privacy caveats remain in the inventory (`src/spendguard/store/configuration/ledger_connection.py:882`, `src/spendguard/egress/saas.py:484`, `src/spendguard/egress/saas.py:527`).

`pull_policy` caches server caps in local config. Advisory caps are displayed suggestions and do not replace local limits; enforced caps resolve to the server ceiling or the smaller local cap, so local config can tighten but cannot loosen the effective policy (`src/spendguard/egress/saas.py:787`, `src/spendguard/egress/saas.py:787`). This resolution contract does not erase the gate's explicit override and fail-open boundaries. Sync reports client-computed ledger/status, truth, decisions and savings; estimated subscription value and guarded savings remain separate from real-cost totals.

Aggregate rows carry deterministic `uid`s; `saas crosscheck` compares local and server rows and reports matching, local-only, server-only and drift states. It excludes estimated-value rows and retains provider/GPU verification gaps rather than treating missing evidence as clean (`src/spendguard/store/configuration/config_store.py:999`). Server implementation and byte-for-byte compatibility cannot be independently established from this client tree.

The **documented external catalog flow** is publication of this repository's `model_catalog.json` → server ingestion into a global curated catalog → anonymous `/api/public/catalog` and `/catalog`, plus authenticated `/v1/models?curated=1` overlays. Source-owned `as_of` dates are distinct from ingestion timestamps ([DATA_PLANE.md](DATA_PLANE.md), `docs/DATA_PLANE.md:149`). The client pull persists overlays above the shipped floor, preserves row dates and leaves existing data intact when unavailable (`src/spendguard/egress/saas.py:177`, `src/spendguard/store/reference_data/model_catalog.py:180`). The server/publication legs are contract documentation, not locally verified server capabilities.

### Event consumers and observability

`spendguard.on_event(callback)` registers `callback(event: dict)` and is also a decorator. The payload includes `kind`, provider/model, cost, decision and available `in_tok`/`out_tok`/`cached_in_tok`; `envelope` preserves it and fills `v`, `type`, unique `id`, UTC `ts`, and, when attribution resolves, `conv_id`/`project` (`src/spendguard/analyze/cost_estimation/estimate.py:70`, `src/spendguard/analyze/cost_estimation/estimate.py:70`). For example, `spendguard.on_event(event_sink)` connects an application's existing sink. **Callbacks run inline:** keep them fast; swallowed exceptions do not make a slow callback asynchronous (`src/spendguard/analyze/cost_estimation/estimate.py:70`).

Set `emit.webhook` or `SPENDGUARD_WEBHOOK` for JSON POSTs, and `emit.otel` or `SPENDGUARD_OTEL` for OpenTelemetry. These environment controls override config and accept explicit off values (`src/spendguard/egress/emit.py:38`). Webhook/OTel delivery uses a bounded daemon-thread queue and drops events when flooded; it is best-effort telemetry, not a durable audit transport (`src/spendguard/egress/emit.py:69`, `src/spendguard/egress/emit.py:81`, `src/spendguard/egress/emit.py:174`). OTel uses the application's global meter/tracer and exporter: counters are `spendguard.cost_usd` (USD) and `gen_ai.client.token.usage` (token), token type is input/output, and spans carry `gen_ai.system`, `gen_ai.request.model`, `gen_ai.operation.name`, available `gen_ai.usage.*_tokens`, and `spendguard.decision` (`src/spendguard/egress/emit.py:107`, `src/spendguard/egress/emit.py:118`).

## Known gaps / design in flight

- Prospective coalescing already exists. Its missing pieces are agentic coalescing policy and per-call deadline/SLA flush, not the accumulation queue itself.
- Durable queues, admission windows and whole-job planning are separate built mechanisms. Queue result truncation and mixed-contract whole-job grouping need explicit design attention.
- Anthropic submit/collect exists, but whole-job batch execution is OpenAI-only and tracker polling is not provider-correct throughout. Optional durable storm execution is not default wiring.
- Codex pool admission hardening exists; broker failure/local fallback weakens a strict host-wide-cap guarantee.
- Gate enforcement is not universal fail-closed coverage. Raw HTTP, LiteLLM, Bedrock and Vertex capture must not be mistaken for pre-spend admission; abandoned streams and fine-tuning cost have gaps.
- Several judgment paths still clip evidence or use mechanical meaning proxies, as identified in their entries. This map records existing behavior rather than asserting compliance with repository rules.
- Bulk/checkpoint budgeting and schema/image/reasoning identity have the limitations listed above; timeout does not imply cancellation or zero bill.
- Semantic pricing-name mapping is a stub; semantic freeform insight validation and residual LLM retag execution remain absent. Soft-deadline cancellation/escalation helpers are not integrated into an active observer.
- Residency measurement and live warning are built. Exact historical context attribution, complete project-proportional receipt allocation, provider truth for every category and independently verified server behavior are not established by this tree.
