B0 revision 9: process-owned ledger fork synchronization audit

Scope and method
The inventory covers the base SQLite ledger connection/admission/schema/read/write
infrastructure, durable spend retries and their MCP scheduler, and every module
with a subsystem lock around base-ledger SQL. Source constructor/use searches used
symgrep across src/spendguard, followed by inspection of owners and child handlers.
No provider request or paid model call was used. References describe this revision.

Per-instance synchronization and OS lock ownership
ledger_writer.py:186 admission and :197 ready Event belong to individual writer
owners. The child handler empties the registry and local owner, so future child
dispatch constructs new owners, admission locks, queue conditions, Future state
and ready Events. Old parent owners are not reused by child dispatch.
config.py:1521 connection stepping RLock and ledger_request_cursor.py:164 fallback
stepping RLock belong to connections/cursors. Pool registry and thread-local pool
are discarded in config.py:1881/1887; the default expiry owner is also discarded.
New child connections and cursors therefore get new locks. This is abandonment,
not an assertion that application-held inherited connection aliases become safe.
ledger_read.py:279/280 request cancellation Event/connection Lock belong to a
request scope, not module-owned process state. New request scopes create fresh
objects. Explicit reuse of an inherited request scope or application-held cursor,
connection, custom WAL cadence or custom expiry coordinator is outside this
module-global audit; those objects must not be shared across processes.
ledger_deadletter.py:21 locked_spend_deadletter_path creates per-call flock file
handles. These locks implement intentional cross-process exclusion, not a Python
dead-thread mutex. A child opening a fresh handle must contend with the parent;
it must not issue LOCK_UN on an inherited shared open-file description. Writer
owner reset closes only the child duplicate of its writer flock handle (:147),
without unlocking the parent's still-live file description.

Scope exclusions
fleet consumer registration uses a separate fleet database; resource_state uses
JSON; emit owns webhook dispatch; vendor_call owns run-id state; dispatch, gate,
provider_tokens, overage, storm routing/coalescing, subscription headroom reports
and provider daemon locks govern provider/config/runtime state rather than the
base-ledger synchronization subsystem. They are not claimed fork-safe by this
audit. Their presence was considered rather than silently excluded by filename.

Structural guard and its exact coverage
ledger_fork_locks.py couples construction and child registration for converted
consumer locks and state owners. Existing ordered config reset remains explicit
to preserve admission-generation accounting and condition-to-lock binding.
tests/test_ledger_fork_lock_inventory.py discovers actual Lock, RLock and Condition
globals and immediate attributes on module-defined singleton owners in all 15
audited modules. It holds the entire inventory in a background thread, forks,
and asserts each child object has a new identity and can acquire without blocking.
A watchdog kills a wedged child. Adding an unregistered global or immediate
singleton lock in those modules fails automatically, without updating a lock list.
The module scope list is explicit: a new module must be added. Locks hidden deeper
in containers, foreign-class singleton owners, lazy runtime-created globals,
Events/Semaphores or application-held per-instance aliases are not auto-discovered.
This guard closes the reported class within the audited inventory; it is not a
claim that arbitrary future package state is automatically covered.
