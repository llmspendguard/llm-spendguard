# External readiness follow-up

`spendguard selfcheck` enforces only the reviewed offline subsets recorded in the capability readiness manifest. A green result is not an OpenSSF badge, Scorecard score, PyPI publication or usability certification.

- **Scorecard:** maintainers must run the current Scorecard runner against the public repository and review its complete result, including live GitHub settings, history, OSV findings and dependency ecosystems outside Actions. Record that result before claiming a score; branch protections, reviews, maintained status, fuzzing, release signatures, dependency update tooling, contributors, packaging, SAST, webhook and badge state remain external checks. The offline binary exception is maintained in [WAIVERS](WAIVERS.md). A scheduled informational runner is future work; it is not part of the blocking offline path.
- **Best Practices Passing:** maintainers complete the [official questionnaire](https://www.bestpractices.dev/en/criteria/0), supplying URLs and human attestations for the entire Passing criteria. Existing documents are evidence of presence, not proof of process quality, expertise or effectiveness.
- **PyPA:** release maintainers validate publication and acceptance against the target index during release. Offline builds cannot verify authentication, upload or live index policy.
- **clig.dev:** CLI maintainers conduct task-based terminal usability review, including interaction, cancellation, recovery and output suitability. Deterministic help/version/error tests cover their explicitly named behavior only.
- **Diátaxis:** documentation maintainers review the existing guided index quickstart with new readers, and assess quadrant quality and navigation. Presence and discoverability are machine checked; instructional effectiveness remains a reader judgement.

## Architectural & code quality follow-up

The architectural manifest items use `src/spendguard/architectural_fitness_baseline.json` as reviewed scope and measurement data. Ratchets preserve the existing debt visibly; they do not certify that debt is absent. Tool versions in the dev extra are the versions used to measure the baseline. Update baselines only after reviewing the complete changed measurements and recording why acceptance is warranted.

- **Complete acyclicity — REVIEWED-N/A:** the complete AST graph includes function-local imports and contains existing cyclic components. The baseline records their full membership and cyclic edges. Decompose these components before claiming no import cycles; the fitness function rejects every new cyclic edge, including additions inside an existing component.
- **Full layering — REVIEWED-N/A:** `config` imports adapters, and `pricing` imports adapters/calls. A fictional core/adapters/surfaces hierarchy would misrepresent current code. The enforced boundary protects the recorded standard-library-only foundation modules from application imports. Extend this boundary as responsibilities are separated.
- **Existing duplication:** the measured symilar significant-line and group counts are accepted existing debt, with an enforced regression ratchet. Review clone groups and consolidate authoritative implementations without confusing repeated declarations with implementation clones.
- **Complexity measurements:** Radon CC includes nested functions. Per-file CC maxima and MI floors are measured independently on each supported Python minor version because tokenizer differences affect logical-line counts. New source files and unsupported Python minors fail closed until their measurements receive review.
- **Full dead-function coverage — REVIEWED-N/A:** Vulture's definite findings are enforced package-wide, with individual compatibility-parameter exceptions carrying reasons. Lower-confidence public functions and dynamically registered entry points need caller review before an allowlist can honestly be established. The gate makes no claim that all unused functions are absent.
- **Full type coverage — REVIEWED-N/A:** the annotated CLI projection models are the recorded clean mypy surface. Expand only with measured clean modules; `py.typed` alone does not demonstrate clean typing. The isolated check deliberately makes no claim about transitive application imports.

The existing registry-backed naming and capability-surface-parity gates are cited in the architectural section and reused unchanged. These are fitness functions for their declared contracts, not an ISO/IEC 5055 score or certification. Radon's metrics are documented at <https://radon.readthedocs.io/en/stable/api.html>; import-linter's boundary contracts are documented at <https://import-linter.readthedocs.io/en/stable/contract_types/>.
